## 1. Windows 中文终端编码问题

### 问题描述

Windows 中文版系统的 Python 默认使用 GBK 编码。当代码中执行 `open(path)` 读取含中文内容或 Unicode 字符（如 R-squared 符号 "R²"）的文件时，会抛出:

```
UnicodeDecodeError: 'gbk' codec can't decode byte ...
```

### 影响范围

- 测试代码中 `print()` 输出含 Unicode 字符（如 R-squared 上标）时可能报错
- 读取含中文内容的 CSV 文件时，如果自动编码检测失败，可能回退到 GBK 但文件实际为 UTF-8

### 解决方案

**对于开发者**:
- 所有 `open()` 调用必须显式指定 `encoding='utf-8'`
- 测试代码中避免在 `print()` 中使用非 ASCII 字符
- 使用 `src/data_io/encoding.py` 中的编码自动检测函数

**对于用户**:
- 如果数据上传后显示乱码，请将 CSV 文件用记事本另存为 UTF-8 编码后重新上传
- 工具内置的编码检测器会自动尝试 UTF-8 和 GBK 两种编码

### 状态

已知限制，已通过编码自动检测和显式 encoding 参数缓解。不会修复（Windows 系统级别行为）。

## 2. LF/CRLF 换行符警告

### 问题描述

在 Windows 环境下使用 Git 时，Git 会检测到文本文件的换行符差异并产生如下警告:

```
warning: CRLF will be replaced by LF in <filename>.
The file will have its original line endings in your working directory
```

### 影响范围

- 所有 `.py`, `.md`, `.toml` 等文本文件
- 不影响代码功能和测试结果

### 解决方案

- 此警告为 Git 在 Windows 上的默认行为，不影响功能
- 如需消除警告，可配置 `git config core.autocrlf true`
- 但不建议全局修改 Git 配置，因为可能影响其他项目

### 状态

已知，不修复。原因: 对功能零影响，修改 Git 全局配置有副作用风险。

## 3. kaleido 依赖与 PNG 导出

### 问题描述

图表 PNG 格式导出依赖 `kaleido` 库 (>= 1.3.0)。kaleido 是一个独立的二进制工具，安装过程可能在以下情况失败:

- 网络受限环境（kaleido 需要下载额外的二进制文件）
- 某些 Linux 发行版缺少系统依赖
- pip 版本过旧导致依赖解析失败

### 影响范围

- PNG 格式的图表导出（含综合报告 ZIP 中的 PNG 图表）
- 不影响的导出: SVG 格式、CSV、Excel、LaTeX、HTML、TXT

### 错误表现

```
ValueError: Image export using the "kaleido" engine requires the kaleido package
```

### 解决方案

1. 安装 kaleido:
   ```bash
   uv pip install kaleido>=1.3.0
   ```

2. 如果 kaleido 安装失败，使用 SVG 作为替代格式（SVG 导出不需要 kaleido）

3. `pyproject.toml` 中已声明 kaleido 依赖，但作为可选依赖（不阻塞核心功能）

### 状态

已知限制。短期: 文档化 + SVG 替代方案。长期: 考虑探索 plotly 的 `to_image()` 替代后端。

## 4. __pycache__ 和 .claude/ 的 gitignore

### 问题描述

以下目录/文件不应提交到 Git:

- `__pycache__/` — Python 字节码缓存目录
- `.claude/` — Claude Code 的内部工作目录

### 当前配置

`.gitignore` 已配置:

```

.claude/

*.pyo
.pytest_cache/
```

### 注意事项

- 修改 `.gitignore` 时不要删除 `.claude/` 排除规则

### 状态

已解决，配置在 `.gitignore` 中。仅需注意不要意外删除现有规则。

## 5. 大文件处理性能

### 问题描述

大文件 (> 50 MB) 在解析、类型检测和回归计算时可能出现性能问题:

- 文件解析时间较长（取决于列数和行数）
- 类型检测需要扫描所有列的唯一值
- OLS 回归的矩阵运算对样本量 O(n*k^2)，k 为自变量数

### 当前限制

| 文件大小 | 行为 |
|---------|------|
| < 50 MB | 正常处理 |
| 50-200 MB | 警告 + 建议使用较小数据集 |
| > 200 MB | 阻止上传 |

### 预览机制

- 默认预览 1000 行，可通过滑块调整
- 预览只影响显示，不影响解析（解析读取全部数据）

### 性能基准（Phase 4.3 已验证）

- 10 万行 x 20 变量 OLS 回归: <= 3 秒 (已达标, 详见 `scripts/benchmark.py`)

### 状态

已通过文件大小限制缓解。Phase 4.3 已完成正式性能基准测试。

## 6. 分类变量编码与 patsy

### 问题描述

工具使用 patsy 的公式接口构建设计矩阵。分类变量通过 `C(var_name)` 语法自动生成虚拟变量。这导致以下行为:

1. **参考类别**: patsy 默认以字母序第一个类别为参考类，用户无法在 UI 中自定义参考类别
2. **虚拟变量命名**: 系数名称变为 `C(education)[T.本科]` 等形式，显示在系数表中
3. **二值变量**: 即使在 UI 中标记为 `binary`，patsy 可能仍生成 `C(var)[T.1]` 形式的系数名

### 影响

- 系数表中的变量名可能包含 patsy 的内部表示
- 无法自定义参考类别
- 交互项涉及分类变量时，系数名更加冗长

### 解决方案

- 在数据上传页手动覆盖变量类型为 "continuous" 可强制以数值形式进入模型
- 对二值变量 (0/1)，覆盖为 continuous 可避免 patsy 虚拟化
- 后续版本考虑添加参考类别选择 UI

### 状态

v1.1.0 已部分解决：
- `build_variable_labels()` 重写后正确解析 patsy 列名，UI 中系数表显示为 `教育水平: 本科` 等可读格式。
- 仍不支持自定义参考类别选择 UI。

### 残余问题 (v1.1.0)

以下与变量标签/分类变量相关的问题仍存在，详见 [第 10 节](#10-v110-已知残余问题)：

- `build_variable_labels()` 的 `spec` 参数未被使用（保留以备后用）
- `_build_variable_labels_for_web()` 与 `build_variable_labels()` 是独立实现，列名格式不同（`var_level` vs `var[T.level]`）

## 7. 会话持久化的局限性

### 问题描述

会话状态通过 JSON 序列化保存到 `.session_cache`。但有如下限制:

1. **pandas DataFrame**: JSON 序列化后丢失数据类型信息（如 int64 → int, Categorical → str）
2. **plotly Figure**: 图表对象不参与持久化（重新打开浏览器后需重新生成）
3. **ModelResult**: 可通过 `_model_result_to_json()` 序列化，但 `_raw_model` (statsmodels 对象) 不持久化
4. **文件大小**: 大数据集序列化可能生成很大的 JSON 文件

### 恢复行为

- 应用启动时检测 `.session_cache`，如果存在则提示用户恢复
- 恢复后 `model_result` 等对象从 JSON 重建（不含 `_raw_model`）
- 图表 (`export_charts`) 在持久化时被跳过

### 状态

已知限制。会话持久化主要用于防止误关闭浏览器导致的数据丢失，不适合长期数据存储。建议使用导出功能保存重要结果。

## 9. 已知的功能限制

### 9.1 支持的回归模型

当前版本支持:
- 普通最小二乘 (OLS) 线性回归
- 二元 Logit 回归（v1.1.0 新增，含 OR 值、ROC 曲线、似然比检验）

仍不支持:
- Probit 回归
- 多层次模型 (MixedLM)
- 面板数据模型 (FE/RE)
- 非线性回归 (NLS)
- 多项/有序 Logit 回归

后续模型规划在 v1.2+ 版本中。

### 9.2 仅支持横截面数据

不支持时间序列分析、面板数据分析、生存分析等。时间变量仅作为普通自变量处理，不进行自相关校正。

### 9.3 Cook's Distance 为近似计算

完整的 Cook's Distance 计算需要 hat matrix (影响矩阵)，当前实现使用简化近似公式:

```
D_i = (r_i^2 / (p * MSE)) * (1/n)
```

这可能导致在杠杆值差异较大的数据中低估某些高杠杆点的 Cook's Distance。

### 9.4 缺失值处理有限

当前仅支持三种缺失值处理策略:
- 删除缺失行
- 均值填充
- 中位数填充

不支持: 多重插补 (Multiple Imputation)、KNN 插补、回归插补等高级方法。

### 9.5 无逐步回归

不支持基于 AIC/BIC/p 值的逐步回归（向前选择/向后剔除）。用户需手动选择变量并比较模型。

### 9.6 无正则化方法

不支持 Ridge/Lasso/Elastic Net 等正则化回归方法。当存在严重多重共线性时，建议:
- 检查 VIF 并剔除高 VIF 变量
- 等待 v1.2 中的 Ridge 支持

### 9.7 图表不支持交互式导出

plotly 图表在应用内是完全交互式的（缩放、悬停提示等），但导出为 PNG/SVG 后变为静态图片。HTML 报告中的图表也以 base64 内嵌的静态图片形式存在。

### 9.8 无用户认证和权限管理

工具设计为单用户本地运行，无用户登录、权限管理、分析历史记录等功能。

## 10. v1.1.0 已知残余问题

> 本节记录 v1.1.0 发布时已识别但尚未修复的次要问题。这些问题不影响核心功能正确性。

### 10.1 `build_variable_labels` 的 `spec` 参数未被使用

#### 问题描述

`build_variable_labels(model_result, spec)` 接受 `spec: ModelSpec` 参数，但函数体内未引用 `spec`。该参数在当前实现中不参与任何逻辑。

#### 影响范围

- 无功能影响。参数保留以备后用（如未来需要基于 spec 的编码信息生成更精确的标签）。

#### 状态

已知。保留参数接口以便未来扩展，当前不影响正确性。

---

### 10.2 Web bridge 不支持 categorical x numeric 交互

#### 问题描述

Web (Pyodide) 版中，分类变量与数值变量的交互项通过 `pd.get_dummies` 路径生成，而非 Streamlit 版使用的 patsy 公式路径。这两种路径对交互项的编码方式不同，导致 Web 版无法正确表示 `C(cat_var) * numeric_var` 形式的交互。

#### 影响范围

- 仅在 Web (Pyodide) 版中出现
- 影响：Web 版中涉及分类变量与数值变量交互的模型可能无法正确拟合或显示
- Streamlit 版通过 patsy 公式正常支持此类交互

#### 状态

已知限制。短期不修复（Pyodide 版无 patsy），用户可使用 Streamlit 版处理此类模型。

---

### 10.3 `_build_variable_labels_for_web()` 与 `build_variable_labels()` 独立实现

#### 问题描述

Web 版和 Streamlit 版各有一个独立的变量标签构建函数：
- `build_variable_labels(model_result, spec)` — Streamlit 版，解析 patsy 列名格式 `var[T.level]`
- `_build_variable_labels_for_web(variable_names, var_types)` — Web 版，解析 `pd.get_dummies` 格式 `var_level`

两个函数列名格式不同，维护时需要同步更新。

#### 影响范围

- 两个函数目前各自独立工作，功能正常
- 长期维护成本：变量标签逻辑变更时需同时修改两个函数

#### 状态

已知。未来可考虑统一为一个函数，通过参数控制输出格式。当前不影响正确性。

---

### 10.4 `ModelSpec.interaction_terms` 仅支持 2-way pairs

#### 问题描述

`ModelSpec.interaction_terms` 的数据结构存储交互项对列表（如 `[("x1", "x2"), ("x1", "x3")]`），每项仅包含两个变量名。这意味着只能表示 2-way 交互（`x1:x2`），无法表示 3-way 交互（`x1:x2:x3`）。

#### 影响范围

- 无法在 UI 中创建三个变量的交互项
- `generate_formula()` 生成的公式仅包含 `var1:var2` 形式
- 对于大多数应用场景，2-way 交互已足够

#### 状态

已知设计限制。未来如果需要支持 3-way 交互，需要将数据结构从 2-tuple 扩展为变长 tuple，并同步更新 UI、公式生成和系数表渲染。

## 补充: 开发过程中的注意事项

### Python 版本

- 开发使用 Python 3.12+，通过 `uv` 管理包
- 不要使用裸 `python` 命令，始终使用 `uv run python`

### 文件路径

- Windows Git Bash 下的 `/tmp/` 映射到 `C:\Users\<user>\AppData\Local\Temp\`
- Windows 原生 Python 把 `/tmp/` 解析为 `C:\tmp\`
- 跨工具传递文件时，使用完整 Windows 路径 (如 `C:\Users\lenovos\AppData\Local\Temp\file.csv`)

### 编码声明

- 所有 Python 源文件必须以 `# encoding: utf-8` 开头
- 所有 `open()` 调用必须显式 `encoding='utf-8'`
- JSON 文件统一使用 UTF-8 编码保存

### 依赖版本

当前关键依赖及其版本约束 (来自 `pyproject.toml`):

```
streamlit>=1.28.0
statsmodels>=0.14.0
pandas>=2.0.0
numpy>=1.24.0
plotly>=5.15.0
openpyxl>=3.1.0
kaleido>=1.3.0

```
